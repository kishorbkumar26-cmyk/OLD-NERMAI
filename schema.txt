1. Overview
This is a document-tree (Firestore-style) schema for NERMAI, a multi-tenant academy platform combining an LMS, ERP, and CRM. Collections are top-level and reference each other by ID (e.g. studentId, batchId) rather than nesting deeply — this keeps documents small, queries fast, and the model scalable to tens of thousands of students across multiple academies.
Module Map
CORE — 5 collections: tenants, users, students, staff, staff_roles
ACADEMIC — 7 collections: batches, batch_memberships, courses, enrollments, subjects, topics, classes
CONTENT — 4 collections: videos, resources, live_sessions, watch_history
TEST ENGINE — 7 collections: tests, test_targets, questions, question_translations, attempts, attempt_answers, daily_quizzes

4. Design Notes
What the base design already gets right
Flat, decoupled collections (students, tests, payments, attendance, messages) instead of deep nesting — production-grade for query performance.
batch_memberships as its own collection cleanly supports transfers, rejoining, and multi-batch / sub-batch students.
The test engine (tests → test_targets → questions → attempts → attempt_answers) is a single abstraction covering overall, weekly, subject, topic, class, batch, and public/free tests.
conversations + messages supports private support chat, admin direct messaging, and broadcast groups from one model.
Improvements folded into this version
question_translations replaces per-language sub-fields on questions, avoiding document-size limits as languages are added.
classId added to questions for chapter-wise revision, analytics, and weak-area detection.
enrollments added so a student can hold multiple courses without overloading batch_memberships with payment state.
wallets and refunds added for scholarships, cancellations, and partial refunds.
staff_roles decouples a staff member from a single fixed designation (faculty / accountant / CRM executive / admin).
access_rules replaces a flat visibility flag with rules that can target a specific batch or access tier.
ledger, transactions, expense_categories, expenses, and income_sources give real double-entry accounting: profit/loss, monthly reports, and cash-flow.
Capacity
10,000–50,000 students comfortably, multiple academies (multi-tenant), high concurrent test usage, and long-term feature expansion.

Is Firestore Scalable Enough?
Yes. 
Firestore fits this use case well: realtime messaging, realtime notifications, attendance, test attempts, free/paid gating, multi-tenant partitioning, CRM pipelines, push notifications, and content-delivery metadata are all core Firestore strengths.
Scales comfortably to 50,000+ students
100,000+ test attempts
1,000,000+ messages
100,000+ notifications
1,000+ concurrent live sessions
Firestore Bottlenecks to Avoid
This schema is already flat by design (§ 3), which sidesteps the three most common Firestore mistakes:
Don't nest messages under a conversation (conversations/{id}/messages/{id}) — a busy thread becomes a write hotspot. Keep messages as a root collection indexed by conversationId, as designed.
Don't nest questions under a test (tests/{id}/questions/{id}) — keep questions root-level, as designed.
Don't store large or unbounded arrays on a document — participant lists over ~100, read-receipt arrays, or growing logs. Move these into their own collection instead of a field.
